## 2. Objective
Build a production-ready, centralized Customer Notifications & Communication Center for JMT Travels at `/account/notifications` and `/account/notifications/:id`. The system provides customers with a consolidated hub to review operational alerts and status updates across visa applications, tour bookings, hotel consultations, flight requests, support tickets, and account activities, while maintaining strict tenant boundary isolation (IDOR defense) and zero leakage of internal administrative metadata.

---

## 3. Existing Notification Architecture Audit
Prior to V5.6, the codebase contained:
- `backend/models/Notification.js`: Mongoose model supporting in-app and mock delivery channels (`IN_APP`, `EMAIL`, `SMS`, `WHATSAPP`).
- `backend/services/notification.js`: Centralized service with HTML template rendering, XSS escaping, sandbox provider dispatch, and basic mark-read helpers.
- `backend/server.js`: Legacy `/api/notifications` routes lacking category filters, unified unread counters, and integration with customer dashboard or V5.5 travel inquiry workflows.
- Tourism and Visa services already emitted business events, but Hotel and Flight inquiries lacked customer notification dispatch.

## 5. API Endpoints
| Method | Endpoint | Description | Auth Required | IDOR Protection |
|---|---|---|---|---|
| `GET` | `/api/account/notifications` | List customer notifications (filters: `unread`, `category`, `page`, `limit`) | Yes (JWT) | `userId = req.user.id` |
| `GET` | `/api/account/notifications/:id` | Retrieve single notification detail | Yes (JWT) | 403 Forbidden if `userId !== req.user.id` |
| `PATCH` | `/api/account/notifications/:id/read` | Mark single notification as read, populates `readAt` | Yes (JWT) | 403 Forbidden if not owned |
| `PATCH` | `/api/account/notifications/read-all` | Mark all customer unread notifications as read | Yes (JWT) | Scoped strictly to `req.user.id` |
| `GET` | `/api/account/dashboard` | Extended to include `summary.unreadNotifications` | Yes (JWT) | Authoritative session count |

## 7. Ownership & Security Model (IDOR QA)
- **Authoritative Identity:** `req.user.id` extracted from verified JWT payload is the sole source of truth.
- **Client Overrides Rejected:** Any `userId` in query parameters or request body is ignored.
- **Strict IDOR Defense:** Access to another customer's notification returns `403 FORBIDDEN` and logs a security audit event (`SUSPICIOUS_IDOR_NOTIFICATION_ACCESS_ATTEMPT`).
- **DTO Sanitization:** Internal operational fields (`provider`, `providerMessageId`, `failureReason`, `retryCount`, `_id`, `__v`, `adminNotes`, storage paths) are stripped before transmission.

---

## 8. Duplicate Prevention & Idempotency
- Explicit `idempotencyKey` supported on `dispatchEvent`.
- Automatic composite key generation: `${eventName}:${userId}:${reference}:${status || ''}`.
- If a record with the same idempotency key already exists, dispatch is suppressed and `{ success: true, isDuplicate: true }` is returned.

## 9. Database Indexes
- `{ userId: 1, read: 1, createdAt: -1 }`: Optimizes unread queries and dashboard count aggregation.
- `{ userId: 1, category: 1, createdAt: -1 }`: Optimizes category-filtered queries and chronological sorting.
