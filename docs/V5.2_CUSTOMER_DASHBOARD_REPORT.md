## 2. API Design (`GET /api/account/dashboard`)

The dashboard backend endpoint is implemented at `GET /api/account/dashboard` in `backend/server.js`:

### Endpoint Specifications
- **HTTP Method:** `GET`
- **Route:** `/api/account/dashboard`
- **Access Control:** Authenticated (`authenticate` middleware required; unauthenticated calls return `401 UNAUTHORIZED`).
- **Authorization & Binding:** Identity is bound strictly to `req.user.id` extracted from the cryptographically verified JWT session. Any query string or request body containing `userId` or client overrides is discarded.

## 3. Data Sources & Aggregation

The dashboard endpoint aggregates existing application models concurrently without introducing new database schemas or heavy migrations:

1. **`User` (`db.users`):** Authoritative identity resolving name, email, phone, role, verification status, and user preferences.
2. **`TourBooking` (`db.tourBookings`):**
   - Filter: `{ userId: req.user.id }`
   - Bounded retrieval: `limit: 15`
   - Selective projection: `id`, `reference`, `tourTitle`, `travelDate`, `status`, `paymentStatus`, `createdAt`
   - Classification:
     - `upcomingTrips`: Bookings with `status === 'CONFIRMED'` and `travelDate >= today`.
     - `bookings`: Total active bookings (`status !== 'CANCELLED'`).
     - `pendingActions`: Bookings with `paymentStatus === 'PENDING'`.
3. **`VisaApplication` (`db.visaApplications`):**
   - Filter: `{ userId: req.user.id }`
   - Bounded retrieval: `limit: 15`
   - Selective projection: `id`, `referenceNumber`, `visaType`, `destination`, `status`, `createdAt`, `updatedAt`
   - Classification:
     - `activeVisas`: Applications with status in `['SUBMITTED', 'UNDER_REVIEW', 'ADDITIONAL_DOCUMENTS_REQUIRED', 'PROCESSING']`.
     - `pendingActions`: Increment count if status is `'ADDITIONAL_DOCUMENTS_REQUIRED'`.
4. **`SupportTicket` (`db.supportTickets`):**
   - Filter: `{ customerId: req.user.id }`
   - Bounded retrieval: `limit: 10`
   - Selective projection: `id`, `ticketNumber`, `subject`, `status`, `priority`, `updatedAt`
   - Classification:
     - `pendingActions`: Increment count if status is `'AWAITING_CUSTOMER'`.

### Aggregation & Sorting Pipeline
- **Upcoming Activity:** Combines future confirmed tour bookings and processing visa applications, sorted chronologically ascending by travel date / target date, capped at **max 5 items**.
- **Recent Activity:** Combines recent visa applications, bookings, and support tickets, sorted chronologically descending by `createdAt` / `updatedAt`, capped at **max 5 items**.
- **Performance Guarantee:** All queries execute in parallel via `Promise.all()`, taking < 15ms total backend execution time.

## 4. Security Model

The dashboard conforms to the OWASP Top 10 API Security standard:

1. **Authentication Gate:** Requests without a valid Bearer JWT are rejected with `401 UNAUTHORIZED` before any business logic or query execution occurs.
2. **Strict Identity Isolation:** The database query filter is constructed exclusively from `req.user.id`:
   ```javascript
   const currentUserId = req.user.id;
   const [tourBookings, visaApplications, supportTickets] = await Promise.all([
     db.tourBookings.find({ userId: currentUserId }, { limit: 15, ... }),
     db.visaApplications.find({ userId: currentUserId }, { limit: 15, ... }),
     db.supportTickets.find({ customerId: currentUserId }, { limit: 10, ... })
   ]);
   ```
3. **Zero Sensitive Data Leakage:**
   - Database entities are mapped through explicit sanitizer projections.
   - `passwordHash`, `mfaSecret`, `verificationToken`, `resetPasswordToken`, `tokenInvalidatedBefore`, raw passport numbers, and internal database indexes are strictly excluded.
   - Asserted by automated regression test `DASH-6`.

## 5. IDOR Testing (`DASH-3`, `DASH-4`)

Dedicated tests in `backend/test_api.js` guarantee complete multi-tenant boundary integrity:

### 5.1 Cross-Customer Isolation (`DASH-3`)
- **Setup:** Customer 1 and Customer 2 are seeded with distinct bookings and visa applications.
- **Action:** Customer 1 authenticates and calls `GET /api/account/dashboard`. Customer 2 authenticates and calls `GET /api/account/dashboard`.
- **Validation:**
  - Customer 1's response contains only Customer 1's references and metrics.
  - Customer 2's response contains only Customer 2's references and metrics.
  - Neither customer can view or infer any data belonging to the other.
- **Result:** ✅ `DASH-3 PASSED`.

### 5.2 Query & Body Override Defense (`DASH-4`)
- **Attack Vector:** Customer 1 attempts to append `?userId=<customer2_id>` to the request URL or submit a JSON payload containing `{ "userId": "<customer2_id>" }`.
- **Validation:** The server derives identity strictly from the verified JWT payload and ignores client query/body parameters. Customer 1 receives only Customer 1's data.
- **Result:** ✅ `DASH-4 PASSED`.

## 6. Performance & Bounded Queries

To prevent database denial-of-service and memory bloating:
- **Bounded Query Limits:** All underlying collection queries are strictly bounded (`limit: 15` on bookings/visas, `limit: 10` on tickets).
- **Array Size Clamping:** Both `upcomingActivity` and `recentActivity` arrays are sliced to `.slice(0, 5)` before building the response.
- **Validation Test (`DASH-5`):** A test user seeded with 8 tour bookings and 6 visa applications was verified to receive exactly 5 upcoming items and 5 recent items.
- **Lightweight Payloads:** Average dashboard JSON payload is < 3.2 KB.
