## 2. Authentication Architecture Preservation

The existing authentication architecture has been strictly preserved with zero breaking changes:
1. **User Identity Model:** Relies on the established `User` model (`backend/models/User.js`) storing account credentials, authentication status (`ACTIVE`, `SUSPENDED`, `DISABLED`), email verification flags, role (`CUSTOMER`, `STAFF`, `ADMIN`, `SUPER_ADMIN`), and localized preferences.
2. **Session Model:** Uses standard JSON Web Tokens (JWT) signed with `HS256`, 7-day expiration (`expiresIn: '7d'`), verified using the environment-authoritative `AUTH_SECRET`.
3. **Middleware Security:** The central `authenticate` middleware in `backend/server.js` decodes bearer tokens, resolves the database user, validates account status against suspension/disablement, and enforces token revocation checks (`tokenInvalidatedBefore`).
4. **Non-Regression:** `/api/auth/register`, `/api/auth/login`, and `/api/auth/me` maintain 100% backward compatibility and behavioral contracts.

## 3. Profile API Endpoints Specification

Two dedicated endpoints have been implemented in `backend/server.js`:

### 3.1 `GET /api/account/profile`
- **Access Control:** Authenticated (`authenticate` middleware required; returns `401 UNAUTHORIZED` if unauthenticated).
- **Binding:** Strictly extracts user identity from `req.user.id`. Ignores any request parameters or client-supplied user IDs.
- **Behavior:**
  - Retrieves `req.user` from the database.
  - Queries `CustomerProfile` by `{ userId: req.user.id }`. If no profile record exists yet, an empty profile structure with `passportNumberMasked: null` is safely returned without error.
  - Formats passport number using `maskPassport(passportNumber)` helper.
  - Returns a clean, sanitized customer profile payload.
- **Success Response (200 OK):**
```json
{
  "success": true,
  "user": {
    "id": "use_e850f5ec-8b3d-40fc-a835-d0f7d65a44e2",
    "name": "Ahmed Al-Harthy",
    "email": "ahmed@jmttravels.com",
    "phone": "+96891234567",
    "role": "CUSTOMER",
    "verified": true,
    "preferredLanguage": "en",
    "preferredCurrency": "OMR"
  },
  "profile": {
    "nationality": "Omani",
    "dateOfBirth": "1988-11-20",
    "address": "Way 2135, Building 45",
    "city": "Muscat",
    "country": "Oman",
    "passportNumberMasked": "••••••4321"
  }
}
```

### 3.2 `PUT /api/account/profile`
- **Access Control:** Authenticated (`authenticate` middleware, rate-limited via `submissionLimiter`).
- **Binding:** Strictly bound to `req.user.id`. Any incoming `userId` in the body is discarded/rejected.
- **Allowed Fields:**
  - `User`: `name`, `phone`, `preferredLanguage`, `preferredCurrency`
  - `CustomerProfile`: `nationality`, `dateOfBirth`, `address`, `city`, `country`
- **Validation Rules:**
  - `name`: String, 2 to 100 characters.
  - `phone`: String, 7 to 25 characters, valid phone format (`+?[\d\s-]{7,25}`).
  - `preferredLanguage`: Must be either `'en'` or `'ar'` (returns `400 INVALID_LANGUAGE`).
  - `preferredCurrency`: Must be one of `['OMR', 'USD', 'AED', 'SAR', 'INR']` (returns `400 INVALID_CURRENCY`).
  - `dateOfBirth`: ISO Date (`YYYY-MM-DD`), must be in the past (returns `400 VALIDATION_ERROR`).
  - `address`, `city`, `country`: Strings, max 100-200 characters.
  - Forbidden/Unrecognized Fields: Attempting to provide arbitrary/unknown keys returns `400 VALIDATION_ERROR`.
- **Atomic Upsert:** If `CustomerProfile` does not exist for the user, it is created with the updated fields; otherwise, it is updated in-place.
- **Audit Logging:** An immutable audit trail entry is created with action `PROFILE_UPDATED`.

## 4. Data Models & Upsert Integration

The system seamlessly combines two distinct domain layers:
1. **`User` Entity (`backend/models/User.js`):**
   - Central authentication identity.
   - Updates applied only to customer-safe fields (`name`, `phone`, `preferredLanguage`, `preferredCurrency`).
2. **`CustomerProfile` Entity (`backend/models/CustomerProfile.js`):**
   - Detailed travel, regional, and identity information.
   - Bound by unique foreign reference `userId: req.user.id`.
   - Contains `passportNumber`, `nationality`, `dateOfBirth`, `address`, `city`, `country`.
   - If a customer registers and accesses `/account/profile` before completing any bookings, the system performs a safe upsert:
     ```javascript
     let existingProfile = await db.customerProfiles.findOne({ userId: req.user.id });
     if (existingProfile) {
       updatedProfile = await db.customerProfiles.update(existingProfile.id, profileUpdates);
     } else {
       updatedProfile = await db.customerProfiles.create({
         userId: req.user.id,
         ...profileUpdates
       });
     }
     ```

## 5. Security Controls & Mass Assignment Defense

To safeguard system integrity and prevent privilege escalation:
- **Mass Assignment Neutralization:** Forbidden security fields (`role`, `status`, `verified`, `passwordHash`, `verificationToken`, `tokenInvalidatedBefore`, `mfaSecret`, `passportNumber`, `userId`) are screened and strictly isolated. An attacker cannot inject `"role": "ADMIN"` or `"verified": true` via `/api/account/profile`.
- **Strict Allowlist Verification:** Any key outside the predefined allowlist triggers an immediate `400 VALIDATION_ERROR` rejection.
- **Rate Limiting:** `PUT /api/account/profile` is guarded by `submissionLimiter` (max 30 submissions per 15 minutes per IP/session), preventing brute-force mutation attacks.

---

## 6. IDOR Defense & Tenant Isolation

- **Authoritative Server Context:** Neither `GET` nor `PUT` accepts a target user ID parameter from the URL query or request body. Identity is derived exclusively from the cryptographically verified JWT (`req.user.id`).
- **Regression Test Confirmation (`PROFILE-10`):** Customer 1 attempting to supply `userId: customer2User.id` in `PUT /api/account/profile` will only update Customer 1's profile. Customer 2's data remains completely untouched and isolated.
- **Cross-Customer Defense:** Customer A cannot view or modify Customer B's profile under any circumstances.

## 8. Passport Masking Strategy & Immutability Justification

### Masking Implementation
A specialized helper function `maskPassport(passport)` formats passport strings:
```javascript
function maskPassport(passport) {
  if (!passport || typeof passport !== 'string') return null;
  const trimmed = passport.trim();
  if (trimmed.length <= 4) {
    return '••••••••';
  }
  const visible = trimmed.slice(-4);
  return `${'•'.repeat(Math.max(6, trimmed.length - 4))}${visible}`;
}
```
- Example: `A12345678` → `••••••5678` (only the last 4 characters visible, all preceding characters converted to bullets).
- For short strings (≤4 characters), an 8-bullet mask is displayed to prevent character leakage.
- Zero raw passport numbers are ever emitted in API responses or audit logs.

### Why Passport Numbers are Read-Only in Self-Service
In travel and visa processing operations:
1. **Visa Integrity:** Passport numbers are tied to official government visa applications (Royal Oman Police, Schengen consular authorities, Saudi MoFA). Changing a passport number online without administrative re-verification could invalidate active or pending visa filings.
2. **Fraud Prevention:** Restricting direct passport mutation prevents account takeovers from altering legal travel identification.
3. **Audit Trail:** Customers requiring passport updates must upload a verified passport copy or contact JMT Support, ensuring compliance with Oman tourism regulations.
4. **UI Guidance:** The frontend displays an explicit `🔒 Read-Only` badge with explanatory helper text: *"Passport numbers are verified against official government visa documents. To update, please submit a passport update request via JMT Support."*
