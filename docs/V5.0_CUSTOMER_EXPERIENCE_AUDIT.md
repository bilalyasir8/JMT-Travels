## 1. CURRENT AUTHENTICATION ARCHITECTURE

### 1.1 User Representation & Data Models
Authenticated users in JMT Travels are represented across two primary database entities:
1. **`User` (`backend/models/User.js`)**: The root identity and authentication credential record.
2. **`CustomerProfile` (`backend/models/CustomerProfile.js`)**: The customer demographic and travel credential profile linked 1:1 via `userId`.

#### User Entity Attributes:
- **Identifier:** `id` (`String`, UUID/nanoid, unique, indexed)
- **Identity:** `name` (`String`, required, trimmed 2–80 chars), `email` (`String`, unique, lowercase, trimmed, indexed), `phone` (`String`, trimmed)
- **Credential:** `passwordHash` (`String`, bcrypt 12 rounds, mandatory, excluded from sanitization)
- **Role System & RBAC:** `role` (`String`, enum: `['CUSTOMER', 'STAFF', 'ADMIN', 'SUPER_ADMIN']`, default: `'CUSTOMER'`, indexed)
- **Lifecycle & Account State:** `status` (`String`, enum: `['ACTIVE', 'UNVERIFIED', 'SUSPENDED', 'DISABLED']`, default: `'ACTIVE'`, indexed)
- **Email Verification:** `verified` (`Boolean`, default: `false`), `verificationToken` (SHA-256 hashed string), `verificationTokenExpires` (`Date`)
- **Password Reset:** `resetPasswordToken` (SHA-256 hashed string), `resetPasswordExpires` (`Date`), `passwordChangedAt` (`Date`)
- **Brute-Force & Lockout:** `failedLoginAttempts` (`Number`, default: 0), `lockUntil` (`Date`, temporary 15-minute lock upon 5 failed attempts)
- **Session Revocation:** `tokenInvalidatedBefore` (`Date`, set on password reset or explicit logout to invalidate existing JWTs)
- **MFA Architecture:** `mfaEnabled` (`Boolean`, default: `false`), `mfaSecret` (`String`, base32 secret, sensitive)
- **Preferences:** `preferredLanguage` (`String`, enum: `['en', 'ar']`, default: `'en'`), `preferredCurrency` (`String`, enum: `['OMR', 'AED', 'SAR', 'INR', 'USD']`, default: `'OMR'`)

#### CustomerProfile Entity Attributes:
- **Identifier:** `id` (`String`, unique, indexed)
- **Foreign Key:** `userId` (`String`, required, unique/indexed, references `User.id`)
- **Travel Documents & Demographics:** `passportNumber` (`String`, trimmed, sensitive), `nationality` (`String`, trimmed), `dateOfBirth` (`String`, YYYY-MM-DD), `address` (`String`), `city` (`String`), `country` (`String`)
- **Compound Index:** `{ userId: 1, passportNumber: 1 }`

### 1.2 JWT & Session Implementation
- **Algorithm & Token Spec:** HMAC-SHA256 (`HS256`) via `jsonwebtoken` (`^9.0.3`).
- **Signature Key:** Loaded from `process.env.AUTH_SECRET`. In development, defaults to `'local-development-jmt-jwt-secret-key'`. In production (`NODE_ENV === 'production'`), startup terminates fatally if `AUTH_SECRET` is unset.
- **Expiration Policy:** 7 days (`expiresIn: '7d'`).
- **Token Claims (`sub`, `role`, `email`):**
  ```json
  {
    "sub": "usr_c4578ef991a0",
    "role": "CUSTOMER",
    "email": "customer@example.com",
    "iat": 1780210000,
    "exp": 1780814800
  }
  ```
  *Security Compliance:* Payload strictly excludes passwords, tokens, secrets, or internal flags.

### 1.3 Authentication Flow & Guard Middleware
- **Header Parsing:** `authenticate` middleware in `backend/server.js` checks:
  1. `Authorization: Bearer <token>`
  2. Fallback cookie: `Cookie: jmt_session=<token>`
  3. Administrative service key: `x-admin-key` header (bypasses JWT if matching `process.env.ADMIN_ACCESS_KEY`)
- **Validation Pipeline:**
  1. Verifies JWT signature and expiry using `jwt.verify(token, AUTH_SECRET)`.
  2. Queries user record: `await db.users.findById(payload.sub)`.
  3. Checks account status: Returns `403 ACCOUNT_SUSPENDED` if `SUSPENDED` or `DISABLED`.
  4. Checks session revocation: Compares token issue time `payload.iat` against `user.tokenInvalidatedBefore`. If `tokenIat < revokedTime`, returns `401 TOKEN_REVOKED`.
  5. Attaches sanitized user record to request context: `req.user = user`.
- **Optional Authentication:** `optionalAuth` populates `req.user` if a valid token is present, but allows guest access to proceed smoothly without 401 errors.
- **Role-Based Access Control (RBAC):** `authorize(...allowedRoles)` middleware enforces required privileges (e.g. `authorize('STAFF', 'ADMIN', 'SUPER_ADMIN')`).

### 1.4 Client-Side State Management
- **Token Storage:** Stored in browser `localStorage` as `'jmt_token'`.
- **User Object Cache:** Stored in browser `localStorage` as `'jmt_user'`.
- **Active Navigation & State:**
  ```javascript
  const state = {
    user: JSON.parse(localStorage.getItem('jmt_user') || 'null'),
    token: localStorage.getItem('jmt_token') || '',
    lang: localStorage.getItem('jmt_lang') || 'en',
    cart: null,
    activeConversationId: localStorage.getItem('jmt_chat_conv') || null
  };
  ```
- **Session Termination / Logout:**
  1. Client calls `POST /api/auth/logout` with Bearer token.
  2. Server updates `user.tokenInvalidatedBefore = new Date()`, immediately invalidating all active tokens for that user.
  3. Client executes `localStorage.removeItem('jmt_token')`, `localStorage.removeItem('jmt_user')`, and redirects to `/`.

## 3. DATA OWNERSHIP MATRIX

The following hierarchy represents the strict relational ownership structure enforced across database collections:

```text
User (id)
 ├── CustomerProfile (userId -> User.id) [1:1]
 │
 ├── VisaApplication (userId -> User.id) [1:N]
 │    ├── VisaDocument (applicationId -> VisaApplication.id AND uploadedBy -> User.id) [1:N]
 │    ├── RequestedDocuments (embedded inside VisaApplication) [1:N]
 │    └── Timeline (embedded inside VisaApplication) [1:N]
 │
 ├── TourBooking (userId -> User.id) [1:N]
 │    ├── BookingTraveller (bookingId -> TourBooking.id) [1:N]
 │    └── Timeline (embedded inside TourBooking) [1:N]
 │
 ├── Payment (userId -> User.id) [1:N]
 │    ├── links to: TourBooking (bookingId -> TourBooking.id) [Optional]
 │    ├── links to: VisaApplication (visaApplicationId -> VisaApplication.id) [Optional]
 │    ├── PaymentEvent (paymentId -> Payment.id) [1:N]
 │    └── Refund (paymentId -> Payment.id) [1:N]
 │
 ├── SupportTicket (userId -> User.id) [1:N]
 │    └── Messages (embedded OR chatMessages linked via conversationId) [1:N]
 │
 ├── ChatConversation (customerId -> User.id) [1:N]
 │    ├── ChatMessage (conversationId -> ChatConversation.id) [1:N]
 │    └── EscalatedTicket (escalatedTicketId -> SupportTicket.id) [Optional 1:1]
 │
 ├── Notification (userId -> User.id) [1:N]
 │
 └── ContactInquiry (linked via email/phone matching User.email/User.phone) [1:N]
```

### Ownership Enforcement Principles:
1. **Authoritative Identification:** Ownership is established solely by server-authenticated `req.user.id`.
2. **Untrusted Client Inputs:** Client request bodies containing `userId`, `customerId`, `actorId`, or `role` are completely ignored.
3. **Compound Foreign Keys:** Resources with secondary ownership (e.g. `VisaDocument`) verify both direct ownership (`uploadedBy === req.user.id`) and parent application ownership (`appRecord.userId === req.user.id`).

### Identified API Architecture Gaps for V5.0:
1. **Missing Customer Profile Endpoints:** There is currently no `GET /api/account/profile` or `PUT /api/account/profile` for customers to inspect or update their own `CustomerProfile` (date of birth, nationality, address, passport number).
2. **Missing Unified "My Trips" Aggregation:** Currently, the frontend must make 3 disjointed calls (`/api/visa/applications`, `/api/tourism/bookings`, `/api/support/tickets`). A dedicated aggregated or standardized query endpoint is needed.
3. **Missing Pagination on Primary Entity Lists:** Both `GET /api/visa/applications` and `GET /api/tourism/bookings` return unbounded arrays (`db.find(filter)`). To sustain V4.1 performance principles, server-side pagination (`page`, `limit`) should be introduced in V5.

## 5. SECURITY & IDOR AUDIT

### 5.1 Analysis of Existing Controls
The codebase demonstrates mature Insecure Direct Object Reference (IDOR) protections implemented in V4.0:
- **Tenant Isolation:** All collection listing queries default to `{ userId: req.user.id }` unless the authenticated user holds an elevated administrative role (`STAFF`, `ADMIN`, `SUPER_ADMIN`).
- **Entity Access Checks:** Individual resource lookups (`:id`) fetch the document and immediately execute an ownership check:
  ```javascript
  const isStaff = ['STAFF', 'ADMIN', 'SUPER_ADMIN'].includes(req.user.role);
  if (!isStaff && entity.userId !== req.user.id) {
    await logAudit(req, 'SUSPICIOUS_IDOR_ATTEMPT', 'RESOURCE_TYPE', req.params.id);
    return res.status(403).json({ success: false, error: { code: 'FORBIDDEN', message: 'Access denied: You do not own this resource.' } });
  }
  ```
- **Audit Logging of Probing Attempts:** Failed ownership checks trigger an automated audit log entry (`db.auditLogs.create`) with `SUSPICIOUS_IDOR_*` tags, enabling staff monitoring of credential or URL enumeration attempts.

### 5.2 Areas Requiring Hardening in V5.0
1. **Guest Booking Re-Association:** When a customer books a tour or submits a visa application as a guest (unauthenticated) using `email@example.com`, and later registers or signs in with that same email, those legacy records currently lack `userId`.
   - *Architecture Requirement:* Provide a secure server-side claim mechanism (e.g. verifying ownership of the guest reference number or email confirmation) before associating unlinked guest records with `req.user.id`. Never expose guest records simply based on an unverified email string in a query.
2. **Document Download URL Tampering:** While `GET /api/documents/:id/download` correctly checks `docRecord.uploadedBy === req.user.id || appRecord.userId === req.user.id`, any future direct file serving route must never expose direct static URLs in `frontend/public/` for private identity documents.

## 7. "MY TRIPS" INFORMATION ARCHITECTURE & UNIFIED VIEW

### 7.1 Concept Definition
A customer's travel experience with JMT Travels frequently involves multi-service journeys. For example:
- A customer traveling to Salalah books a **Tour Package** ("Salalah Khareef Escape") and submits an **Oman Tourist Visa Application**.
- Another customer traveling to Europe submits a **Schengen Visa Application** and books an **Oman Air Flight** via concierge inquiry.

### 7.2 The Unified "Trip" Synthesis Model
Rather than creating an artificial, rigid new collection in MongoDB (which would duplicate data and introduce sync bugs), the V5.0 Customer Portal will implement an **Authoritative Read Aggregation Model**:

```text
┌─────────────────────────────────────────────────────────────┐
│                 SYNTHESIZED "TRIP" OBJECT                   │
├─────────────────────────────────────────────────────────────┤
│ • tripId: Synthesized deterministic ID                      │
│ • title: Destination or Primary Service Name                │
│ • destination: Country / City                               │
│ • travelDates: { departureDate, returnDate }                │
│ • status: 'UPCOMING' | 'ONGOING' | 'COMPLETED' | 'ACTION_REQ'│
│ • components:                                               │
│   ├── tours: [ TourBooking records ]                        │
│   ├── visas: [ VisaApplication records ]                    │
│   ├── inquiries: [ Hotel/Flight ContactInquiries ]          │
│   ├── documents: [ Linked VisaDocuments ]                   │
│   └── payments: [ Linked Payment records ]                  │
└─────────────────────────────────────────────────────────────┘
```

#### Trip Grouping Logic:
1. **Primary Cluster:** Group records sharing matching destinations and proximate travel dates (±7 days).
2. **Fallback Cluster:** Standalone bookings or visa applications operate as self-contained trips.
3. **Trip Status Computation:**
   - `ACTION_REQUIRED`: If any linked visa is in `ADDITIONAL_DOCUMENTS_REQUIRED` or booking is in `PAYMENT_PENDING`.
   - `UPCOMING`: If travel date is in the future and status is `CONFIRMED` / `APPROVED` / `PROCESSING`.
   - `ONGOING`: If current date falls between travel start and estimated duration.
   - `COMPLETED`: If travel date has passed or status is `COMPLETED`.

## 12. PERFORMANCE & SCALABILITY CONSIDERATIONS

The Customer Portal will strictly adhere to V4.1 Performance Foundation rules:
1. **Bounded Data Payloads:** Entity listing endpoints will support `page` and `limit` query parameters with a default limit of 10 items.
2. **MongoDB Query Projection:** Database queries will project only customer-facing fields, excluding heavy internal audit arrays or unneeded fields.
3. **HTTP Response Compression:** Gzip/Brotli compression middleware (`compression()`) ensures dashboard JSON payloads remain under 5 KB.
4. **Client-Side Request Deduplication:** The frontend `apiCall()` deduplication cache prevents duplicate simultaneous network requests during tab switching.
5. **Image Optimization:** All thumbnails, package hero graphics, and hotel images will serve optimized WebP assets with explicit width/height attributes and lazy loading.

## 13. SECURITY THREAT MODEL

| Threat Category | Potential Attack Vector | Existing Control | Required V5.0 Hardening |
|---|---|---|---|
| **IDOR** | Attacker substitutes another user's `id` in `/api/visa/applications/:id` | Server checks `app.userId === req.user.id` | Audit logging triggers automatically; maintain zero trust of query parameters. |
| **IDOR (Documents)** | Attacker attempts to download another user's passport via `/api/documents/:id/download` | Checks `doc.uploadedBy === user \|\| app.userId === user` | Prohibit direct static paths in web server; streaming only through authenticated controller. |
| **Broken Access Control** | Customer attempts to access staff endpoints (`/api/admin/*`) | `authorize('STAFF', 'ADMIN')` blocks access | Verified 403 response on all administrative routes. |
| **Credential Tampering** | Attacker modifies role or permissions in request payload | Mass assignment protection in controllers | Role assignment strictly hardcoded on backend; client input ignored. |
| **Session Hijacking** | Stolen JWT used after password reset or logout | `tokenInvalidatedBefore` checks token `iat` | Tokens issued before revocation timestamp immediately return 401. |
| **Data Exposure** | Password hash, MFA secret, or gateway secrets in API responses | `sanitizeUser()`, `sanitizePayment()` | Enforce automated regression tests verifying sanitization. |
| **CSRF / Injections** | Malicious HTML in customer support tickets or chat | `escapeHTML()` sanitization across notification and email templates | Continue strict sanitization of all dynamic string interpolations. |

## 15. AUDIT RISK ASSESSMENT

1. **Risk:** Unauthenticated legacy guest bookings not appearing in customer dashboard.  
   *Mitigation:* Provide an authenticated "Claim Past Booking" workflow verifying booking reference and email verification token.
2. **Risk:** Overloading database with unindexed compound queries.  
   *Mitigation:* All primary query filters (`userId: req.user.id`, `createdAt: -1`) already have compound indexes in Mongoose models.
3. **Risk:** Exposing staff notes (`adminNotes`).  
   *Mitigation:* Mongoose schema sets `{ select: false }` on `adminNotes` in `VisaApplication.js`; service layer sanitization explicitly deletes `adminNotes`.
4. **Risk:** Payment gateway disruption.  
   *Mitigation:* Payment gateways (PayTabs/Thawani) remain **strictly on hold**; portal displays read-only payment logs without triggering gateway checkout flows.
