## 4. Data Modeling & Aggregation Strategy

The unified trip journey does not introduce redundant relational models. Instead, it computes customer journeys dynamically via an optimized aggregation layer:

```
                          Customer Account (req.user.id)
                                        │
           ┌────────────────────────────┼────────────────────────────┐
           ▼                            ▼                            ▼
      TourBookings              VisaApplications             ContactInquiries
  (Status, Dates, Pax)        (Status, Type, Docs)      (Hotel / Flight Inquiries)
           │                            │                            │
           └────────────────────────────┼────────────────────────────┘
                                        ▼
                            Trip Aggregation Pipeline
                          (Grouped by Journey / Reference)
                                        │
                                        ▼
                                Unified Trip DTO
                ┌──────────────────────────────────────────────┐
                │ id, tripNumber, title, destination, status   │
                │ startDate, endDate, travellers, heroImage    │
                │ services: [ Tour, Visa, Hotel, Flight ]      │
                │ documents: [ sanitized streaming links ]     │
                │ payments: [ sanitized payment references ]   │
                └──────────────────────────────────────────────┘
```

### Aggregation Rules:
1. **Primary Journey Anchor:** Each `TourBooking` acts as a primary trip entity. Associated `VisaApplication` records (matching the user, destination, or date window) are linked as visa services.
2. **Standalone Visa Journeys:** When a customer holds an active `VisaApplication` without an attached tour package, it is elevated into a dedicated "Visa Journey" with travel milestones.
3. **Consultation Inquiries:** Unlinked hotel or flight requests from `ContactInquiry` appear as "Hotel Consultation" or "Flight Consultation" within the journey timeline.
4. **Lifecycle State Machine:**
   - **`ACTION_REQUIRED`**: Unpaid tour bookings (`PAYMENT_PENDING`), visas requiring document re-upload, or pending traveler actions.
   - **`UPCOMING`**: Confirmed bookings where `travelDate > today`.
   - **`ONGOING`**: Trips currently in progress (`startDate <= today <= endDate`).
   - **`COMPLETED`**: Historical trips where travel has concluded.

## 5. Backend Implementation Details

### Endpoints Implemented in `backend/server.js`

#### 1. `GET /api/account/my-trips`
- **Protection:** `authenticate` middleware required; returns 401 if unauthenticated.
- **Query Parameter:** `?status=ALL|UPCOMING|ONGOING|ACTION_REQUIRED|COMPLETED` (validated server-side; invalid values rejected with 400).
- **IDOR Protection:** Customer identity is strictly bound to `req.user.id`. Any incoming `userId` in query parameters or request body is disregarded.
- **Bounded Queries:** Customer bookings, visas, and inquiries are queried with concurrency caps and max record limits to eliminate unconstrained memory usage.

#### 2. `GET /api/account/my-trips/:id`
- **Protection:** `authenticate` middleware required.
- **Tenant Validation:** Matches the requested trip identifier against the authenticated customer's aggregated trips.
- **Strict 404 Response:** Attempts by Customer B to access Customer A's trip return 404 `NOT_FOUND` (preventing reference enumeration).

## 6. Security & Data Protection

| Security Vector | Implementation Detail | Test Verification |
| :--- | :--- | :--- |
| **Authentication Defense** | Unauthenticated requests to `/api/account/my-trips` or `/api/account/my-trips/:id` return `401 UNAUTHORIZED`. | `TRIP-1` |
| **Tenant Isolation (IDOR)** | Customer A and Customer B datasets are strictly segregated. Cross-tenant access attempts return 404 or empty sets. | `TRIP-3` |
| **Query/Body Spoofing** | Injections such as `?userId=victim_id` or `{ userId: "victim_id" }` are ignored. | `TRIP-4` |
| **Passport Data Masking** | Passports are strictly masked using `•••••• + last 4 digits` (e.g. `••••••5432`). Full passport numbers are never returned. | `TRIP-7` |
| **Payment Secrets Hygiene** | Gateway keys, webhook signatures, and provider metadata are stripped from the payment sub-DTO. | `TRIP-8` |
| **Document Access Isolation** | Storage keys are hidden; document downloads route through authenticated token-validated streaming endpoints. | `TRIP-9` |
| **Sensitive Field Stripping** | Passwords, hashes, verification tokens, reset tokens, and salt values are excluded from all responses. | `TRIP-6` |

## 11. Performance & Query Optimization

1. **Index-Assisted Data Retrieval:** Lookups across `tourBookings`, `visaApplications`, and `payments` leverage existing indexes on `userId` and `applicationId`.
2. **Bounded Result Windows:** Queries fetch only relevant records within bounded time and count limits, preventing unbounded in-memory joins.
3. **No Heavy Database Cascades:** Trips are synthesized via pure functional transformations in Node.js memory, eliminating multiple round-trip database round-trips.

---

## 12. Error Handling & Edge Cases

- **Zero Trips State:** New accounts with no bookings or visas receive an empty list with a helpful callout inviting them to browse tour packages.
- **Unverified Accounts:** Customers who have not verified their email see a gentle warning banner on their dashboard and trips page encouraging email confirmation.
- **Invalid Filter Query:** Passing `?status=MALICIOUS_INPUT` returns a clear `400 VALIDATION_ERROR` response rather than falling back to an unhandled query exception.
