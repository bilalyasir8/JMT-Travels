## 1. Executive Summary

Phase V5.4 delivers a customer-facing Visa Application management center and cryptographically secured Document Vault for the JMT Travels luxury travel portal. Customers can now inspect their active visa applications (`/account/visa`), review authoritative milestone timelines and applicant details (`/account/visa/:id`), upload required or missing verification documents, securely download stored documents via authenticated binary streams, and safely replace outdated documents with zero risk of file loss.

All operations enforce strict tenant boundaries (IDOR defense), privacy guarantees (masked passport numbers, excluded internal notes, stripped physical storage keys), and multi-layer abuse protection (Section 9A, Section 13A, and Section 15A).

---

## 2. Pre-Implementation Audit Findings

Prior to making any code modifications, an audit of the existing codebase was conducted:
1. **Existing Models:** Inspected `VisaApplication` and `VisaDocument` models. `VisaDocument.status` originally supported `UPLOADED`, `VERIFIED`, `REJECTED`. It lacked explicit `REPLACED` tracking, which was added alongside `replacesDocumentId` and `replacedByDocumentId`.
2. **Existing Storage Service:** `backend/services/storage.js` used local filesystem abstraction with UUID-based keys. It required hardening to reject empty files (0 bytes), long filenames (> 255 chars), archive formats (`.zip`, `.rar`, `.7z`, etc.), and executable files.
3. **Existing Controllers:** `backend/services/visa.js` had `uploadDocument` but lacked an atomic `replaceDocument` method and orphan file cleanup on DB insertion failures.
4. **Endpoint Mappings:** Authenticated routes `/api/account/visa`, `/api/account/visa/:id`, `/api/account/documents`, and `/api/documents/:id/replace` were missing and have now been established.

## 8. Authenticated Document Download Flow

Endpoint: `GET /api/documents/:id/download`
- **Authentication:** Requires valid Bearer JWT. Unauthenticated requests are rejected with `401 UNAUTHORIZED`.
- **Authorization & IDOR Defense:** Verifies that `doc.uploadedBy === req.user.id` or user has staff role (`STAFF`, `ADMIN`, `SUPER_ADMIN`). Cross-customer download attempts are rejected with `403 FORBIDDEN`.
- **Path Traversal Defense:** Storage keys are strictly validated and resolved within the designated storage directory.
- **Binary Streaming:** Serves the file as an attachment stream with sanitized headers:
  - `Content-Type: <mimeType>`
  - `Content-Disposition: attachment; filename="<sanitized_filename>"`
  - `X-Content-Type-Options: nosniff`
- **Client Implementation:** The frontend executes an authenticated `fetch` with the `Authorization` header, receives the Blob stream, and triggers a clean browser download, preventing auth token leakage in URL query parameters.

---

## 9. Secure Document Upload Architecture

Endpoint: `POST /api/documents/upload`
- **Rate Limiting:** Guarded by `uploadLimiter` (100 uploads per 15 minutes per IP/user).
- **Body & Size Limits:** Max 10MB per file.
- **Storage Isolation:** Physical file is saved with a non-guessable UUID storage key inside isolated storage.
- **Sanitized DTO:** Response excludes internal physical storage keys and MongoDB metadata (`_id`, `__v`).

---

## 10. Document Replacement Flow & Consistency (Section 13A)

Endpoint: `POST /api/documents/:id/replace`
- **Replacement Atomicity (Section 13A):**
  1. Validates the incoming replacement file completely (magic bytes, size, abuse checks).
  2. Persists the new replacement document to physical storage and creates the new DB record first.
  3. Safely updates the old document: status transitions to `REPLACED`, and bidirectional pointers (`replacesDocumentId`, `replacedByDocumentId`) are set.
  4. If storing the new file or writing the DB record fails at any point, the old document remains 100% active and untouched—never losing valid customer documents.
- **Ownership Verification:** Cross-customer replacement attempts are blocked with `403 FORBIDDEN`.

---

## 11. Storage & Database Consistency Protections (Section 15A)

- **Orphan File Prevention:** If the database write fails after a file has been written to disk, the catch block unlinks the physical file from storage.
- **Orphan DB Record Prevention:** No DB document is ever created unless the file has been successfully written to disk and verified.
- **Safe Recovery:** Failed uploads leave zero trace in either the filesystem or database collections.

---

## 12. Upload Abuse Protections (Section 9A)

Both client-side and server-side storage abuse protections are strictly enforced:
1. **Empty File Rejection:** Files with `0 bytes` are rejected immediately with `400 BAD_REQUEST`.
2. **Body & Size Limit:** Files exceeding 10MB are rejected.
3. **Filename Length Limit:** Filenames exceeding 255 characters are rejected.
4. **Archive Format Block:** Archive extensions (`.zip`, `.rar`, `.7z`, `.tar`, `.gz`, `.bz2`, `.iso`, `.dmg`) are rejected.
5. **Executable Format Block:** Executable extensions (`.exe`, `.sh`, `.bat`, `.cmd`, `.msi`, `.com`, `.scr`, `.vbs`, `.js`, `.jar`, `.bin`) are rejected.
6. **MIME & Magic Bytes Validation:** File headers are inspected to verify consistency with declared types.

---

## 13. IDOR Defense & Authorization Boundaries

Strict identity enforcement across all V5.4 endpoints:
- Identity is derived exclusively from the verified JWT payload (`req.user.id`).
- Query parameter overrides (e.g. `?userId=victim_id`) are completely ignored.
- Body overrides (e.g. `{ userId: "victim_id" }`) are completely ignored.
- Cross-customer access attempts trigger immediate `403 FORBIDDEN` and an audit security log event (`SUSPICIOUS_IDOR_DOC_ATTEMPT`, `SUSPICIOUS_IDOR_VISA_ATTEMPT`).
- Uploading a document linked to an application owned by another customer is blocked with `403 FORBIDDEN`.

---

## 14. Privacy & Sensitive Field Protection

1. **Passport Number Masking:**
   - All customer-facing endpoints mask passport numbers in the format `••••••5432` (preserving only the last 4 characters).
   - Only staff/admin endpoints reveal the full passport number for verified immigration processing.
2. **Storage Path Redaction:**
   - Raw physical filesystem paths and `storageKey` values are stripped from all customer DTOs.
3. **Internal Notes Redaction:**
   - `adminNotes` and internal staff discussions are omitted from all customer visa application payloads.
